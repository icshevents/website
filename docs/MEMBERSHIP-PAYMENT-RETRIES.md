# Membership application and payment retries

26 October 2026: an unpaid applicant can resubmit matching details to continue the same saved application. The organiser view keeps one application reference and its existing payment ledger. A retry does not create a new Bigin Contact or overwrite personal details.

The existing email/mobile uniqueness constraints remain. The resume RPC matches all submitted answers (including DOB, declarations and joining/renewal choice), category and fee against the saved live application; equivalent UK mobile formats are accepted. A match receives a fresh, hashed, 24-hour capability for the public receipt and payment routes only. The original capability stays valid. No saved personal answers are disclosed. Changed answers, a different applicant, deleted/free/test applications and already-paid records cannot use this recovery path. Active Bigin members and identity conflicts remain blocked; the preliminary form check recognises the matching pending application where Bigin's inactive pending Contact would otherwise require review.

The final application submit path tries resume before inserting. If identical concurrent requests race, the uniqueness failure triggers one resume lookup. This preserves one application under concurrency. Payment completion updates that application's existing ledger and activation; no duplicate application is created.

An open Stripe Checkout is reused. A paid or processing Checkout is never replaced. A retrieved and validated expired Checkout can be retired and replaced using a new persisted attempt number and Stripe idempotency key. A failed completed asynchronous Checkout can only be replaced after its unpaid PaymentIntent is confirmed cancelled; a requires-payment-method intent is cancelled first. Retired sessions remain in a private history table, and delayed events for those known retired sessions do not overwrite the current attempt. Concurrent retries share the same new attempt. Unknown creation outcomes retain their existing idempotency window and require organiser review beyond it.

The payment-return page offers the existing payment control for unpaid applications, including an expired Checkout. Retrying creates no charge by itself; the applicant completes payment on Stripe. The capability is never included in a URL or stored in browser storage.

Apply `database/membership-application-retry.sql` before deploying this source. Its tables use RLS, no public policies and server-role-only grants. The application, payment and activation records remain private.
